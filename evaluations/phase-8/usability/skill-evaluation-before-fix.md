# Phase 8 독립 사용성 평가 — K-DAPI 스킬

평가일: 2026-11-17  
평가 범위: 질문 라우팅, 확인 질문, 답변 깊이, 다중턴 문맥, 웹 미사용 시 정직성  
사용 자료: `SKILL.md`, `docs/QUESTION_ROUTING.md`, `docs/RESPONSE_MODES.md`, `docs/GENERAL_USER_GUIDE.md`, 제공된 `scripts/route_question.py` 실행 결과만 사용했다. 개발 저장소, 평가 정답, 다른 답변 파일은 읽지 않았다. 실제 심층 리서치는 수행하지 않았다.

## 1. 단일턴 10문항

아래의 ‘권장 분류’는 문서 규칙을 질문의 실제 의도에 적용한 결과다. ‘첫 응답’은 조사 결과가 아니라 에이전트가 사용자에게 실제로 보여 줄 짧은 시작 답변 또는 확인 질문이다.

### 1) “토큰증권이 뭐야?”

- 권장 분류: 주 `CONCEPT_EXPLANATION`, 보조 `TOKENIZED_ASSET_OR_RWA`
- 깊이: `QUICK`
- 한국 맥락: 없음. 사용자가 한국을 명시하지 않았으므로 자동 부착하지 않는다.
- 첫 응답 예시: “토큰증권은 주식·채권·수익권 같은 **증권상의 권리**를 분산원장 기반 토큰 형태로 표시한 것입니다. 단순한 코인과 달리 보유자가 갖는 법적 권리, 발행·유통 규제, 원장과 실제 권리의 연결이 핵심입니다.”
- 판정: 적절. 제공 라우터도 동일하게 분류했다.

### 2) “한국에서 토큰증권 지금 발행할 수 있어?”

- 권장 분류: 주 `TOKENIZED_ASSET_OR_RWA`, 보조 `LAW_AND_REGULATION`
- 깊이: `STANDARD`
- 한국 맥락: 포함
- 최신 검증: 필수. ‘지금’의 시행법, 시행 예정 제도, 아직 확정되지 않은 정책을 분리해야 한다.
- 첫 응답 예시: “발행 가능 여부는 토큰이 나타내는 권리와 발행 구조에 따라 달라집니다. 최신 한국 법령과 시행 상태를 확인해 **현재 가능한 구조·시행 예정 제도·아직 미확정인 부분**으로 나눠 설명하겠습니다. 구상 중인 기초자산이 있다면 함께 알려주세요.”
- 판정: 대체로 적절. 라우터의 주 유형은 맞지만 법률 상태 판단이 질문의 핵심이므로 `LAW_AND_REGULATION`을 보조 유형으로 유지하는 편이 안전하다.

### 3) “이 코인 어떤 거야?”

- 권장 분류: `AMBIGUOUS_REQUEST`
- 깊이: 분석 전 확인
- 첫 응답 예시: “어떤 코인인지 확인할 수 있게 **이름이나 티커, 사용 네트워크**를 알려주세요. 거래소 화면이나 공식 URL을 보내주셔도 됩니다.”
- 판정: 적절. 임의로 대상을 추측하지 않고 필요한 식별정보를 한 번에 묻는다.

### 4) “이 코인 사도 돼?”

- 권장 분류: 주 `INVESTMENT_OR_PRICE_REQUEST`; 대상 불명확으로 확인 질문 필요
- 깊이: `STANDARD`를 유지하되 우선 안전 전환
- 첫 응답 예시: “매수 여부를 대신 결정해 드리지는 않지만, 구조·공급·기술·운영·규제 위험은 점검해 드릴 수 있습니다. **코인 이름이나 티커와 네트워크**를 알려주세요.”
- 판정: 적절. 단순 거절이 아니라 분석 가능한 대안을 제시한다.

### 5) “솔라나 백서 검토해 줘.”

- 권장 분류: `WHITEPAPER_REVIEW`
- 깊이: `STANDARD`
- 확인 질문: 필수 아님. 프로젝트명이 이미 있으므로 공식 백서를 식별할 수 있다. 특정 버전이나 첨부 문서를 뜻하는 경우에만 추가 확인한다.
- 첫 응답 예시: “네. **솔라나 공식 백서의 발행처와 버전부터 확인**한 뒤, 기술 주장·토크노믹스·권한 구조와 현재 구현 상태를 구분해 검토하겠습니다. 특정 파일이나 버전을 뜻했다면 보내주세요.”
- 판정: 문서 규칙상 바로 시작 가능. 그러나 제공 라우터는 ‘백서 파일이나 공식 URL, 프로젝트명’을 요구하면서 이미 제시된 프로젝트명을 인식하지 못해 불필요한 확인 질문을 생성했다.

### 6) “업비트에서 거래되는 솔라나의 네트워크를 평가해 줘.”

- 권장 분류: 주 `NETWORK_OR_PROTOCOL_REVIEW`; 업비트 언급은 자산 식별 및 한국 이용 맥락일 뿐, 거래지원 정책 질문은 아니다.
- 깊이: `STANDARD`
- 한국 맥락: 포함하되 네트워크 품질 평가와 업비트의 거래지원 판단을 혼합하지 않는다.
- 첫 응답 예시: “솔라나 네트워크를 합의 구조, 처리 성능, 검증자·탈중앙화, 실제 사용, 장애 이력과 업그레이드 위험 기준으로 평가하겠습니다. 업비트 거래지원 여부는 네트워크 품질이나 규제 적합성을 보증하는 근거로 보지 않겠습니다.”
- 판정: **핵심 라우팅 실패.** 제공 라우터는 ‘업비트에서 거래’라는 표현만으로 `EXCHANGE_SUPPORT_POLICY`로 오분류했다. 질문은 상장 사유·유의·종료 정책을 묻지 않는다.

### 7) “USDC 관련 미국 법률을 설명해 줘.”

- 권장 분류: 주 `LAW_AND_REGULATION`, 보조 `STABLECOIN_REVIEW`
- 깊이: `STANDARD`
- 한국 맥락: 없음
- 최신 검증: 필수. 미국의 법률·법안·감독지침을 구분해야 한다.
- 첫 응답 예시: “미국에서 USDC에 관련되는 규칙을 **현재 시행 중인 법률, 계류 중인 법안, 감독기관 지침**으로 나눠 설명하겠습니다. 특히 발행자, 준비자산·상환, AML/제재, 이용자 보호에 미치는 영향을 구분하겠습니다.”
- 판정: 제공 라우터는 `STABLECOIN_REVIEW`만 반환했다. 대상이 USDC이더라도 사용자의 중심 의도는 ‘미국 법률 설명’이므로 법률 유형이 빠지는 것은 중요한 누락이다.

### 8) “클래리티법 알려줘.”

- 권장 분류: 우선 `AMBIGUOUS_REQUEST`; 사용자가 미국 디지털자산 시장구조의 `CLARITY Act`를 뜻한다고 확인하면 `LAW_AND_REGULATION`
- 깊이: 확인 후 보통 `STANDARD` 또는 간단 설명이면 `QUICK`
- 첫 응답 예시: “어떤 ‘클래리티법’을 뜻하시나요? **미국 디지털자산 시장구조 법안인 CLARITY Act**를 말씀하시는지, 다른 국가·분야의 법률인지 알려주세요.”
- 판정: **식별 실패.** 제공 라우터는 법안·국가 확인 없이 `CONCEPT_EXPLANATION`으로 분류했다. 비슷한 이름의 문서를 임의로 선택하지 말라는 스킬 규칙과 충돌한다.

### 9) “한국에서 이더리움과 솔라나의 차이는 뭐야?”

- 권장 분류: 주 `CONCEPT_EXPLANATION`, 보조 `NETWORK_OR_PROTOCOL_REVIEW`
- 깊이: `QUICK`(사용자가 평가·심층 비교를 요구한 것은 아님)
- 한국 맥락: 포함. 기술 차이와 한국 내 이용·거래 맥락을 구분한다.
- 첫 응답 예시: “한국에서도 두 자산의 **기술적 차이 자체는 같습니다**. 이더리움은 범용 스마트계약 생태계와 높은 분산성을 중시하고, 솔라나는 빠른 처리와 낮은 수수료를 중시합니다. 국내 거래소 이용·규제 차이까지 원하시면 그 부분을 따로 나눠 설명하겠습니다.”
- 판정: **핵심 라우팅 실패.** 제공 라우터는 이를 `REGULATORY_COMPARISON`으로 보고 ‘비교할 해외 법률’을 되물었다. 사용자는 두 네트워크의 차이를 물었지 두 관할권 규제를 비교해 달라고 하지 않았다.

### 10) “CLARITY Act랑 한국 규제를 비교해 줘.”

- 권장 분류: `REGULATORY_COMPARISON`
- 깊이: `STANDARD`
- 한국 맥락: 포함
- 최신 검증: 양쪽 공식 원문과 현재 시행 상태 확인 필요
- 첫 응답 예시: “미국 CLARITY Act와 한국 규제를 **적용 대상, 자산 분류, 감독기관 권한, 사업자 의무, 이용자 보호, 현재 입법·시행 상태** 기준으로 비교하겠습니다. 법안과 현행법을 같은 수준의 제도로 취급하지 않겠습니다.”
- 판정: 적절. 제공 라우터도 동일하게 분류했다.

## 2. 다중턴 문맥 유지 평가

### A. 법안 → 한국 → 핵심 차이 표

**턴 1 사용자:** “클래리티법 알려줘.”  
**응답:** “미국 디지털자산 시장구조 법안인 CLARITY Act를 말씀하시는 건가요? 맞다면 법안의 목적·적용 대상·현재 입법 상태를 구분해 설명하겠습니다.”

**턴 2 사용자:** “맞아. 그럼 한국에서는?”  
**응답:** “한국 쪽 대응 체계를 묻는 것으로 이해했습니다. 미국 CLARITY Act와 1:1로 같은 단일 법률이 있다고 전제하지 않고, 한국의 현행 디지털자산 규율과 관련 입법 상태를 같은 기능별 항목으로 대응시켜 설명하겠습니다.”

**턴 3 사용자:** “핵심 차이 표로.”  
**응답:**

| 항목 | 미국 CLARITY Act | 한국 규제 |
|---|---|---|
| 문서 성격 | 최신 입법 상태를 확인해야 하는 특정 법안 | 현행법·하위규정·추진 중 입법을 구분해야 하는 규제 체계 |
| 자산 분류 | 법안이 정한 분류와 감독 권한 배분이 핵심 | 국내 법률상 자산 성격과 서비스 유형별 적용 규정이 핵심 |
| 감독 구조 | 법안 원문상 기관별 권한 확인 필요 | 국내 관계기관의 법정 권한과 실제 적용 범위 확인 필요 |
| 비교 주의 | 통과·공포·시행 여부를 구분 | 현행·예정·미확정을 구분 |

**판정:** 문맥 유지 성공. 2턴의 “한국에서는?”를 별도 한국 개론으로 초기화하지 않고 CLARITY Act의 비교 대상으로 해석하며, 3턴의 “표”도 같은 비교 범위를 유지한다. 단, 실제 답변에서는 최신 공식 원문 확인 후 구체 내용을 채워야 한다.

### B. 지시어 코인 → LINK → 실제 사용 → 위험

**턴 1 사용자:** “이 코인 어떤 거야?”  
**응답:** “코인 이름이나 티커, 사용 네트워크를 알려주세요.”

**턴 2 사용자:** “LINK.”  
**응답:** “Chainlink의 LINK로 이해했습니다. LINK는 Chainlink 오라클 네트워크에서 노드 운영 보상·스테이킹 등 생태계 기능에 쓰이는 토큰입니다. 같은 티커의 다른 자산을 뜻한다면 네트워크나 공식 URL을 알려주세요.”

**턴 3 사용자:** “실제 사용은?”  
**응답:** “Chainlink의 실제 사용을 묻는 것으로 이어서 보겠습니다. 가격 피드 같은 데이터 오라클, 체인 간 메시징, 준비자산·자산 데이터 제공 등 어떤 서비스가 실제 운영 중인지와 LINK 토큰 수요가 그 사용과 어떻게 연결되는지를 구분해 확인해야 합니다.”

**턴 4 사용자:** “위험은?”  
**응답:** “같은 Chainlink/LINK 기준으로, 오라클·노드 운영의 중앙화 및 장애 위험, 외부 데이터 품질, 스마트계약·브리지 보안, 경쟁 프로토콜, 토큰 공급·인센티브, 규제 위험을 나눠 보겠습니다. 프로젝트 측 채택 주장은 독립 검증된 사용량과 구분해야 합니다.”

**판정:** 문맥 유지 성공. 2턴에서 대상을 확정한 뒤 3·4턴에서 다시 코인명을 요구하지 않고 Chainlink/LINK의 실제 사용과 위험으로 자연스럽게 좁힌다. 또한 ‘네트워크 사용’과 ‘LINK 토큰 가치·수요’를 동일시하지 않는다.

### C. 이더리움 평가 → 솔라나 비교 → 쉽게 설명

**턴 1 사용자:** “이더리움 평가해 줘.”  
**응답:** “이더리움을 네트워크 기준으로 평가하겠습니다. 합의·검증자 구조, 탈중앙화, 실제 사용, 확장성, 업그레이드와 장애·의존성 위험을 중심으로 보고, ETH 가격 전망과는 분리하겠습니다.”

**턴 2 사용자:** “솔라나랑 비교해 줘.”  
**응답:** “앞의 이더리움 네트워크 평가 기준을 그대로 유지해 솔라나와 비교하겠습니다. 핵심 축은 탈중앙화·검증자 요구사항, 처리량·수수료, 실행·확장 방식, 생태계 사용, 장애와 업그레이드 위험입니다.”

**턴 3 사용자:** “쉽게 설명해.”  
**응답:** “쉽게 말하면, 이더리움은 참여자가 많고 검증이 넓게 분산된 ‘큰 공용 기반시설’에 가깝고, 솔라나는 빠르고 저렴한 처리를 중시한 ‘고성능 단일망’에 가깝습니다. 이더리움은 혼잡과 비용을 보조망으로 나눠 해결하고, 솔라나는 한 네트워크에서 많은 처리를 하려는 차이가 큽니다. 어느 쪽이 무조건 우월하다기보다 분산성·속도·비용의 우선순위가 다릅니다.”

**판정:** 문맥 유지 성공. ‘쉽게 설명해’를 새 개념 질문으로 초기화하지 않고 바로 앞의 이더리움–솔라나 비교를 간단한 언어로 재표현한다.

## 3. 웹 미사용 조건의 최신 상태 질문

**사용자:** “CLARITY Act의 현재 입법 상태를 알려줘.”

**적절한 실제 응답 예시:**

> 현재 웹을 사용할 수 없어 **CLARITY Act의 2026-11-17 현재 입법 상태를 최신 공식 원문으로 검증할 수 없습니다.** 비실시간 지식만으로 발의·위원회 처리·본회의 통과·대통령 서명·시행 여부를 단정하지 않겠습니다. Congress.gov의 해당 회기 법안 페이지에서 법안 번호, `Latest Action`, 통과된 의회, 대통령 조치와 날짜를 확인해야 합니다. 공식 링크나 원문을 주시면 그 자료의 진위는 별도 확인 대상으로 표시하고, 확인 가능한 범위에서 상태를 구분해 드리겠습니다.

**판정:** 통과. 답변 앞부분에서 최신 검증 불가를 명시하고, 기억에 의존해 상태를 단정하지 않으며, 확인해야 할 공식 필드를 제시한다. 단순히 “정보가 오래될 수 있다”는 꼬리표만 붙이는 것보다 명확하다.

## 4. 핵심 실패 요약

1. **키워드 과적합:** ‘업비트에서 거래되는’이라는 수식어 때문에 네트워크 평가를 거래소 정책 질문으로 오분류한다.
2. **‘한국에서’의 의미 과대해석:** 한국에서 두 네트워크의 차이를 묻는 질문을 규제의 국가 간 비교로 바꾸고, 존재하지 않는 해외 법률 정보를 되묻는다.
3. **법안 식별 부족:** ‘클래리티법’처럼 음역된 불완전한 법안명을 개념 설명으로 처리하며 법안명·국가 확인 질문을 생략한다.
4. **중심 의도 누락:** “USDC 관련 미국 법률”에서 스테이블코인 대상만 잡고 법률 분석 유형을 누락한다.
5. **이미 제공된 식별정보 재요청:** “솔라나 백서”에 프로젝트명이 있는데도 프로젝트명을 다시 요구한다.
6. **복합 유형 보존 부족:** 현재 발행 가능성이나 특정 자산 관련 법률처럼 구조와 법률 상태가 함께 필요한 질문에서 보조 유형이 충분히 남지 않는다.

종합하면, 문서 자체의 수동 라우팅 원칙·깊이 정책·오프라인 정직성은 실사용에 충분히 명확하다. 가장 큰 사용성 위험은 제공된 결정적 라우터가 표면 키워드에 과도하게 반응해 사용자 의도를 바꾸는 점이다. 에이전트는 라우터 결과를 최종 판정으로 쓰지 말고 문맥 검토로 교정해야 한다.
